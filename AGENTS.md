# Lexful UAT Playwright suite

Start Feature Specific TCs from the server. Preflight, the Stytch session, and the context pack are written under `runs/tickets/<ticket>/<date>_<time>Z_<id>/` before OpenCode starts. The server also writes `e2e-coverage.md` there. Author must not rewrite a case that file already lists for search, asset crud, or document editing. Specs for the remaining behavior go in that folder's `specs/` directory. Each new test has one type tag (`@positive`, `@negative`, `@edge`) and one suite tag (`@bvt`, `@smoke`, `@sanity`, `@regression`). There is no fixed count. The checked-in suite lives in `e2e test cases/`. E2E User Journey TCs are `runs/phase-1/`. A product bug is recorded in `bugs.md`. `runs/START-HERE.txt` maps the rest.

```bash
npm run serve
npm run ticket -- LEX-3371
```

`npm run ticket` starts Feature Specific TCs and prints `run.log` until it finishes. If that ticket is already in progress, it follows that run. Add `--new` to start another one.

Use the model. One `qa` agent owns functional QA: Explore and Author in one session, then Heal in a new session that reads the run files (`FEATURE.md`, `explore/flow.md`, `feature-map.md`), then Promote; or E2E heal-only on phase-1. The UI/UX audit also runs in its own session and the server renders `ux-report.html` from its JSON with `scripts/generate_ux_report.py`. Do not spawn subagents. Procedure: `.agents/skills/lexful-autonomous-agent-qa/SKILL.md` and `.agents/prompts/qa.md`. A case the walk never reached is a gap, not a product bug. A gap the ticket or its pull request requires, or leftover fixtures named in the UX audit, keeps the run in revision. The server runs Playwright and writes `qa-result.json` in the same run folder. UI/UX audit uses the `ux-auditor` agent when `QA_RUN_UX_AUDIT=true`. Before the run is sealed, passing journeys are copied into `e2e test cases` using `playwright/test-outcomes.json`. The default Stytch session for `STYTCH_PERSONA` is `runs/cache/stytch/session.json`. `node scripts/persona.mjs support` or `viewer` signs in as that role and writes `runs/cache/stytch/<persona>.json` without replacing the default. Set `BEDROCK_API_KEY` in `.env`. The container maps it to `AWS_BEARER_TOKEN_BEDROCK` for OpenCode.

`npm run e2e` runs E2E User Journey TCs on their own, in a folder under `runs/phase-1/`. That run does not call Linear. With `QA_PHASE1_ON_START=true` (default), every ticket run starts with the E2E User Journey stage after preflight, against the same build, and keeps it in that run's `e2e/` folder; a ticket never creates a separate phase-1 run. `false` skips the stage. Container start never auto-runs E2E.

One trigger, one run: `POST /run/<ticket>`, `POST /run/pr/<n>` (or `npm run ticket -- --pr <n>`), `POST /trigger/uat-deploy` (`sha`, `pr`, `ticket`) or, without the server, `python -m app.cli --sha <sha>` for a container started per UAT deploy (docs/setup.md). The run records its trigger in `manifest.json`. A PR or deploy trigger is resolved to its ticket before the folder is made, so the run starts under `runs/tickets/<ticket>/`; a run folder is never moved or renamed, and its result is in `index.json` and `manifest.json`. Every run fetches the product repo and checks out the commits the deployment record says UAT runs (`source-info.md`).

`pr-brief.md` is the context pack without its patches. The server keeps a read-only clone of the product repo under `runs/source/` (PR branches fetched as `pr-<n>`, token never stored) and names it in `source-info.md`; the agent browses it with Read, Grep, Glob, and `git log|show|blame|grep|diff`, and writes `feature-map.md` before it plans tests. A backend ticket also uses the API lane: `node scripts/api-probe.mjs [--persona all] GET /v1/...` calls UAT with the saved sessions. Findings go in `api-findings.json` (each with an `id`); the server files them in `bugs.md` even when every test passes. Recreate the container after changing `.env`.

Run flow and files added by the server: preflight checks the GitHub deployment record and halts when a merged PR is not on UAT (`QA_ALLOW_UNDEPLOYED=true` overrides). `pr-brief.md` numbers the criteria (AC1...) and carries review and Linear comments; `history.md` lists earlier runs of the ticket. The agent writes `feature-map.md`, `hypotheses.json` (every Risk tried), `coverage.json` (every AC mapped to test ids, a gap, or `na`), and `affected-cases.json` (checked-in cases the diff touches). Specs import `test` from `qa-fixtures.ts`, which records console errors and failed API calls into `playwright/signals.jsonl`. Playwright runs each test on the next free of `QA_PW_WORKERS` workers (`QA_PW_FULLY_PARALLEL`), so every test must pass alone; a describe that cannot declares `test.describe.configure({ mode: 'serial' })`. The UX audit runs beside Playwright and heal; its lines are in `run.log`, marked `ux-audit`. The server renders `ux-report.html` with the UX kit's generator and checks it with `scripts/check_report_contract.py` (`.agents/ux/report-contract.md`); a failing report is an open issue. After heal the server runs the affected cases, then a fresh verify session reproduces suspected findings (`verify.json`). A heal that changes an expectation is recorded in `assertion-edits.json` and keeps the run in revision. Every run ends with a `── run summary` block in `run.log` and `summary.json`: each phase, its status and time, where it stopped, tests, bugs, cost. OpenCode and Playwright run as the `qa` user (`QA_AGENT_USER`), so they cannot read the server's secrets. A dropped model connection resumes the session once (`QA_AGENT_RETRIES`). `POST /runs/cancel-all` stops the processes of a running run.

Bugs and the report: the agent writes each defect as the bug object of skill §8 (`triage.json` `bugs[]`, `api-findings.json`); the server does not write bug text and does not file a failure the agent did not describe. Before a bug is filed, a fresh `verify` session follows its steps, saves a screenshot to `bug-evidence/<ref>.png` and returns the steps it used; Playwright's failure screenshot of the affected test is copied there too. A bug the verifier cannot reproduce is not filed; for the checked-in suite it goes back to the next heal as outdated test work. `bugs.json` is the record and `bugs.md` renders each bug as a ticket. `linear-report.md` (and `linear-report.html`, the same report for a browser) is the one report of a run: the trigger, the E2E stage and its bugs, the ticket's tests by type and suite and its bugs, the UX audit's suggested changes, and links to `ux-report.html` and the screenshots. Nothing is sent to Linear or GitHub from the harness yet. The E2E heal keeps `e2e test cases/` true to the app: it updates locators, copy and seeded data in place, and a failing case is outdated until the product is shown to be wrong. A sealed run keeps only its record (`runs/START-HERE.txt` lists it): the reports, bugs and screenshots, specs, plan and walk notes, `playwright/test-outcomes.json`, the hand-off and heal notes, the E2E stage's results and bugs, and the explore, heal and verify transcripts as `.gz`. Raw Playwright output, probe logs, prompts and other scratch go once the bugs hold their screenshots; the server prunes older runs the same way at start. A halted or failed run keeps everything.

Stay inside this directory. Do not read `~/Downloads`, `~/Desktop`, `~/Documents`, or any other checkout. Do not clone `docu-stack` yourself; use the read-only clone the server made.

- Linear access is the named ticket plus the parent, children, and related issues on that ticket.
- GitHub access is the pull requests that mention that ticket, and only the files in those pull requests.
- Do not commit `.env`, `auth-state.json`, or `runs/`.
