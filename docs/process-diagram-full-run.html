lexful-qx-harness

How the harness works

One server runs the whole pipeline. One agent (qa) on one model does every piece of AI work, one session per phase, and the files in the run folder are its only memory between sessions. The server runs Playwright, checks the agent's files and decides the verdict.

The parts

docker container · :8787

Server · FastAPI

The orchestrator. It queues runs (one at a time), runs preflight, starts every agent session, runs Playwright, checks the agent's files, files bugs and writes the verdict and reports.

Agent · qa on OpenCode

One agent, one model (OPENCODE_MAIN_MODEL, Haiku 5.5 on Bedrock). No subagents. It reads .agents/prompts/qa.md and the one phase file the server names. It works as an unprivileged user and cannot read the keys.

Tools the agent uses

  • playwright-cli for the browser
  • scripts/api-probe.mjs and persona.mjs for the API and other roles
  • scripts/lookup.mjs to fetch a ticket or PR the context names, through the server, with a budget

What it reads

  • Linear: the ticket, its parent, children and related issues (read-only)
  • GitHub: the pull requests that mention the ticket and the files in them (read-only)
  • The product repo, cloned read-only at the commit UAT runs
  • Live UAT in a real browser. No local app is started

Where the rules live

  • .agents/prompts/qa.md: rules every phase shares, and the phase to file map
  • .agents/skills/lexful-autonomous-agent-qa/phases/: one file per phase
  • references/: test design, context, bug objects, API lane
  • Behavior is written in these skills, not in server code

1 · Trigger

npm run ticket · POST /runs

Something starts the harness

  • docker compose exec harness npm run ticket -- LEX-1234, or -- --pr 2245
  • A UAT deploy workflow on GitHub, through the QA machine's runner
  • A sha that is already running is skipped. Each run gets its own folder under runs/

Ticket from a pull request

The ticket key (LEX-n) is read from the PR title, then branch, then body. A PR with no key cannot be matched to a ticket.

2 · Preflight

no agent yet

Gates

Secret, payload and a LEX- key. A failed gate stops the run as HALTED.

Sign-in

A saved Stytch session for UAT, renewed from .env while a run is active.

Deployment

The merged PR must be on UAT, or the run halts (QA_ALLOW_UNDEPLOYED overrides).

Context pack

The full ticket, comments, connected issues, PRs and images are saved under context/. pr-brief.md is the index.

Halt

Failed gate, sign-in or deployment check. The run records HALTED and no agent starts.

The server runs e2e test cases/ on live UAT (search, asset crud, document editing). Nothing is authored here. The agent is called only for failures, in the e2e-heal phase.

Heal loop · up to 3 sessions
Server runs the suitePlaywright, 3 workers, each test to the next free worker
all pass ends the stage · failures enter the loop

qa · e2e-heal

A failing case is outdated until proven otherwise. The agent replays it and patches the spec or page object in place (a moved locator, changed data, a new required step, a short wait). It never changes what a case expects.

Three outcomes

  • Patched: the server re-runs only what did not pass, then every spec in an edited folder
  • Bug: reproduced twice, then confirmed by a fresh session before it is filed
  • Needs a decision: the app changed on purpose and the case disagrees; a person decides
Green suite · stage ends Drift patched · logged in changes.log Product bug or decision · in the report

1 · explore + author
qa

Map, walk, probe, write

Reads the brief and the context/ files it needs, maps the change from the diff, lists risks and walks the live app.

  1. Plans each case with a Fails when column
  2. Probes the API and exercises behavior on its own records
  3. Writes specs, coverage.json, hypotheses.json
2 · Playwright (server)
server

Run the specs

Runs only the ticket's specs, test by test, and records every outcome and runtime signal.

  1. Compares expectations before and after any heal
  2. Checks the hand-off files parse
  3. Failures go to heal
3 · heal, up to 3 fresh sessions
qa

Fix how, never what

Locators, waits and fixtures may change. A matcher and its expected value may not.

  1. Wrong product result: a bug with steps
  2. A test that measured badly: a better source, same matcher
  3. Disagreement with a deliberate change: needs a decision
PERFECT · suite green, nothing open NEEDS_REVISION · failures, gaps or decisions remain HALTED · no specs, or a gate failed

5 · UX audit, affected cases, verify, promote

same agent, own sessions

UX audit

Runs beside Playwright and heal. It audits the journey against the UX kit and writes ux-report.html, checked against the report contract. It may raise a suspected functional defect for verify.

Affected cases

Checked-in cases that touch the changed area run beside the ticket. A failure is healed like any E2E case.

Verify

After the UX audit. A fresh session follows the steps of every suspected bug. Only what it reproduces is written to bugs.md with a screenshot.

Promote

At most two passing journeys, only if they fit search, asset crud or document editing, stay true later, and are new. The default is to promote nothing.
