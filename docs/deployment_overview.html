How it runs after a UAT deploy

When a build reaches UAT, GitHub tells a QA machine. The machine runs the harness, which tests the change on UAT and writes a report for the ticket. This page shows how the pieces connect and what Lexful sets up.

Setup checklist

Ticked items are already in hand. Secrets go to the QA team directly, never in a ticket or chat.

StatusWhatWhy
Already in hand
✓ In hand UAT test accounts Test accounts in the "E2E Demo" organization. The harness signs in to UAT as them.
✓ In hand AWS Bedrock access The Claude Haiku 5.5 model in us-east-1. Put a spend limit on the key. The AI model that runs the tests.
✓ In hand The harness, the setup script and the QA workflow Built and in the qa-harness repo. Nothing for Lexful to build. Runs a test from a ticket, a pull request or a deployed commit.
Needed from Lexful
Needed GitHub: a QA-bot account and its token A dedicated bot user with read access to docu-stack, and a personal access token limited to pull requests, deployments and environments. Read-only. Replaces the personal token we test with. The harness reads the pull request and checks the change is on UAT.
Needed Linear: a QA-bot account and its API key A dedicated user in the Lexful workspace, a member of the LEX team. Read-only for now; the same account will later post the report and file bugs, so they show as written by the bot. Replaces the personal key we test with. Reads the ticket and its acceptance criteria.
Needed GitHub: the event listener in docu-stack One workflow file, qa-notify.yml. It starts when the UAT deploy workflows finish successfully and sends the commit id to Lexful-ai/qa-harness. We provide the file. This is the trigger. Without it nothing starts by itself; runs can still be started by hand.
Needed GitHub: a dispatch token, stored as a secret A second token (not the read-only one), or a GitHub App, limited to the qa-harness repo. Save it in docu-stack as QA_HARNESS_DISPATCH_TOKEN. Lets the listener send the event. It can touch nothing else.
Needed GitHub: which deploys start QA For example the docu-app and docu-service UAT deploys. Confirm that a successful deploy means the build is live on UAT. QA should start only when the new build is serving.
Needed GitHub: admin access to qa-harness for one setup step An admin registers the QA machine as a runner. Turn on branch protection for main. Only reviewed code runs on the QA machine.
Needed Network: allow the QA machine through CloudFront Add its public IP to the allow rules for the UAT site. We send the IP. UAT answers bursts of automated traffic with a 403. In our test runs this was the main reason tests failed.
To decide
Decide Who hosts the QA machine One always-on Mac or Linux machine with Docker that does not sleep. Its public IP goes into the CloudFront rule above. It runs the harness after every deploy.
Decide Linear: where bug tickets go The team, project and labels for tickets the QA bot files. Needed only when posting to Linear is switched on. Keeps filed bugs out of the wrong backlog.

What the QA team runs

One machine that stays on and online. It needs Docker, and it must not sleep. Setup is three commands.

# on the QA machine
git clone https://github.com/Lexful-ai/qa-harness.git && cd qa-harness
./build.sh            # first run creates .env; fill in the keys, then run it again
./build.sh --runner   # registers this machine as the runner for the qa-harness repo

Keys stay in a file on that machine only. Each run is saved in a folder there, one folder per ticket, with an HTML report.

Where it stands

Works today

  • Run on demand from a ticket, a pull request or a deployed commit
  • Finds the ticket from the pull request or commit on its own
  • Report per run: test results, bugs with screenshots, UX audit
  • One-command setup of the QA machine

Next

  • Start by itself after each deploy (needs the listener above)
  • Post to Linear: the report as a comment, bugs as tickets
  • Several tickets in one deploy, tested in one pass
  • Tidy-up of old run folders on the machine

Order of setup

  1. Lexful: create the QA-bot accounts for GitHub and Linear, send their tokens, and add the CloudFront allow rule.
  2. QA team: set up the QA machine and register it, then start one run by hand to check it end to end.
  3. Lexful: add the event listener and the dispatch token to docu-stack.
  4. Both: watch the first few deploys. Every UAT deploy now produces a report.
  5. Later: decide on Linear write access, then turn on comments and bug tickets.
